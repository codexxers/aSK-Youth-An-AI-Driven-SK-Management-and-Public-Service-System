 Chapter 3 — diagram generation prompts (aSK//YOUTH.AI)

Use each block as a standalone prompt for a diagramming tool (Mermaid, draw.io, Lucidchart, Napkin AI, etc.). Convention: Treat the system as fully realized including the professor’s mandatory features (login, SK-patterned events including yearly view, responsive mobile UI, youth suggestions, admin reporting)—even if implementation is still rolling out—so all Chapter 3 figures stay internally consistent.

Mandatory SK / governance framing: Events align with Sangguniang Kabataan (SK) practice—categories (sports, seminar, scholarship, assembly, etc.), barangay youth programs, budgets, attendance-style fields where relevant.

 Figure 1 — Conceptual Framework

Generated figure (vector): [`diagrams/figure-1-conceptual-framework.svg`](./diagrams/figure-1-conceptual-framework.svg) — open in browser or insert into Word/PDF. See also [`diagrams/figure-1-conceptual-framework.md`](./diagrams/figure-1-conceptual-framework.md) for embed + export notes.

Prompt

> Draw a horizontal conceptual framework for aSK//YOUTH.AI, a web-based AI assistant for SK-aligned youth programs in the Philippines. Use three main boxes: INPUT (left), PROCESS (center), OUTPUT (right), with bold arrows.  
> INPUT: (1) Youth and SK officers as users, (2) program documents (PDF/DOCX), (3) event data and yearly SK calendars, (4) suggestions/feedback text, (5) admin parameters for reports.  
> PROCESS: Split the center into stacked sub-processes: Secure access (login & roles), AI reasoning (LLM + RAG over documents), Event management (SK-patterned, yearly view), Mobile-responsive UI (Vercel-hosted SPA), Suggestions intake, Admin analytics & report generation; show Cloudflare Tunnel bridging public internet to on-premise inference PC (Node + Python + GPU).  
> OUTPUT: (1) grounded chat answers, (2) event listings and schedules, (3) exported reports (PDF/DOCX), (4) dashboards for attendance/budget trends, (5) acknowledged suggestions.  
> Style: clean academic diagram, black/white or one accent color, labels readable at thesis print size.

 Figure 5 — System Architecture

Prompt

> Produce a technical system architecture diagram for aSK//YOUTH.AI (deployment + apps + data).  
> Client tier: Browser (desktop + mobile viewport); include login screen before main app.  
> Edge tier: Vercel hosts built Vite/React SPA; Cloudflare terminates TLS, routes api. hostname through Cloudflare Tunnel (`cloudflared`) to origin.  
> Application tier (on-premise PC): Node.js Express — auth middleware, REST/SSE chat (`/api/chat/stream`), events CRUD (`/api/events`), suggestions API, admin report endpoints, rate limiting behind proxy, CORS; node-llama-cpp with CUDA for Qwen 2.5 7B GGUF; Python FastAPI service for embeddings, intent, summarization, OCR pipeline; SQLite files for events, users/roles, suggestions, report snapshots.  
> Integration: show arrows Vercel → API, API ↔ Python, API ↔ SQLite, LLM ↔ VRAM.  
> Label mandatory features in callouts. Use layered boxes (presentation / application / data / infrastructure).

 Figure 6 — Use Case Diagram

Prompt

> Draw a UML use case diagram. Actors: Youth / Resident, SK Officer / Moderator, System Administrator, External Service (optional: email or SMS as secondary actor). System boundary rectangle labeled aSK//YOUTH.AI.  
> Youth use cases: Login; Chat with AI (upload documents); View events (SK-patterned); Filter yearly programs; Submit suggestion; Use mobile layout.  
> SK Officer: Login; Create/Edit/Cancel event; Import or attach program memo; View suggestions (read-only or triage).  
> Administrator: Login; Configure roles; Access reports (attendance, budget, demographics); Export PDF/DOCX; Audit logs (high-level).  
> Include relationships where logical (e.g. Chat includes Document upload). Extend optional (e.g. Export report extends View analytics). Keep ≤ 18 use cases for readability.

 Figure 7 — ERD (Entity–Relationship Diagram)

Prompt

> Design an ERD (Chen or crow’s foot notation) for aSK//YOUTH.AI including future-complete schema for professor requirements.  
> Entities: `User` (id, email, password_hash, role enum [youth, sk_officer, admin]), `Session` or `AuthToken`; `Event` (id, title, description, category, date, time, location, organizer, status, requirements, contact, attendees, gender splits, staff_count, budget_allotted, fiscal_year or recurrence flag for yearly programs, SK_barangay_ref); `Suggestion` (id, user_id FK, body, status, created_at); `ChatThread` / `Message` (optional normalization); `Document` / `Attachment` linked to thread; `ReportDefinition` / `ReportRun` (admin exports, parameters, format); `VectorIndexMetadata` (thread_id, chunk refs)—can be simplified to one `RAG_Context` table or note “vector store” as separate store.  
> Show 1:N User→Suggestions, User→Events (created_by), N:M optional Event↔Staff. Mark PK/FK. Thesis-ready, grayscale.
